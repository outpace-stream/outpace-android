# App updates from GitHub releases: design

Date: 2026-11-14

## Intent

The app is distributed as a signed APK on the releases page of
`outpace-stream/outpace-android`, outside any store. Nothing tells a user that a newer app
exists, so people stay on old builds. The app should notice new releases on its own, tell the
user, and let them update in a couple of presses, on phones and on Android TV.

This is about the **app** itself. Engine versions (the `outpace` binary the app downloads from
`outpace-stream/outpace-engine`) already have their own screen and are not touched here.

## Goals

1. **Automatic prompt.** When a newer stable app release exists, the main screen shows a dialog
   with the installed and latest versions, the release notes shown inline (scrollable, loaded in
   the background), and three buttons, left to right:
   - **Update**: downloads, verifies and installs the new APK;
   - **Not now**: closes the dialog for now (it can come back after the next daily check);
   - **Never ask again**: turns the automatic dialog off.
   (Revised 2026-11-14 after review of the first build: a separate Changelog button made four
   actions, which was too busy.)
2. **Updates section in Settings**, always available whatever was dismissed:
   - installed version and latest known version (with when it was last checked);
   - **Check now**;
   - **Changelog** and **Update**, enabled when a newer version is known;
   - a **Notify me about updates** switch. "Never ask again" turns it off; turning it back on
     re-enables the dialog.
3. Works on phones and Android TV (D-pad focus, no browser needed).

## Non-goals

- Updating from any source other than GitHub releases of `outpace-stream/outpace-android`.
- Pre-releases. Only stable `vX.Y.Z` releases count. (No "include pre-releases" switch for the
  app; the engine's existing switch does not apply.)
- Silent or background installs. Android always shows its own install confirmation.
- Background checks while the app is closed (no WorkManager job, no notification).
- Downgrades, rollbacks or picking an older app version.
- Updating unsigned local builds or debug builds.

## Anti-goals (a failure even if it works)

- The dialog interrupting playback, or appearing over a stream opened from an `acestream://`
  link or shared text.
- Nagging: more than one automatic check per day, or showing the dialog again after "Never ask
  again".
- Error popups the user did not ask for. A failed automatic check is silent.
- Installing an APK that was not verified against the release's `.sha256` file.
- Burning the unauthenticated GitHub API quota (60 requests/hour per IP, shared on a household
  network) on routine checks.
- Unbounded files: old downloaded APKs piling up in storage.

## Constraints and facts from the codebase

- **Release format** (from `.github/workflows/release.yml`): tag `vX.Y.Z`, assets
  `outpace-android-X.Y.Z.apk` and `outpace-android-X.Y.Z.apk.sha256` (output of `sha256sum`,
  so `<hex>  <filename>`). Release notes are generated by GitHub (`--generate-notes`), so the
  body is Markdown: PR titles, authors and links.
- **Versions**: `versionName` is the tag without `v`; local builds are `0.0.0`. `versionCode`
  is `major*1_000_000 + minor*1_000 + patch`.
- **Signing**: every release is signed with the same CI key, so Android accepts a release APK
  as an update over an installed release. A debug or locally built APK has a different
  signature and the install fails; the app never offers updates on `0.0.0` builds.
- **Existing code to reuse** (engine release handling):
  - `core/Releases.kt`: `versionFromLatestRedirect`, `compareVersions`, list parsing. Its
    constants are hardcoded to the engine repo; generalise so both repos can use it, without
    changing engine behaviour.
  - `net/EngineReleases.kt`: "latest" via the `https://github.com/<repo>/releases/latest`
    redirect (not the API), cached a day, following a few redirect hops.
  - `net/Http.kt`: `redirectLocation`, bounded `get`, cancellable `download` with progress.
  - `core/Sha256.kt` for verification.
  - `Prefs.kt`: add new keys. Do **not** reuse `latest_version` / `latest_checked_at`; those are
    the engine's.
  - `ui/BatteryPrompt.kt` + `MainActivity` line ~167 (`BatteryPrompt.maybeShow`): the pattern
    for a one-shot prompt on the main screen.
  - `ui/SettingsScreen.kt` builds groups from rows (`row`, `toggle`); the "About" text already
    shows `BuildConfig.VERSION_NAME`.
- **No dependencies**: the app uses plain Views and `org.json`, no AndroidX. Keep it that way.
- `minSdk` 21, `targetSdk` 36.
- Repo rules (`AGENTS.md`): bounded polling and storage, docs updated with user-visible changes,
  run `./gradlew --no-daemon testDebugUnitTest lintDebug assembleRelease` and the identifier
  hygiene check.

## How it works

### Checking

- **Latest version** comes from the `releases/latest` redirect of `outpace-stream/outpace-android`,
  exactly like the engine. GitHub's "latest" never points at a pre-release or draft, so this also
  gives "stable only". No API call is needed to decide whether an update exists.
- **Automatic check** (decision: builder's call, settled after review): when `MainActivity` comes
  to the foreground, refresh the cached latest version if `app_latest_checked_at` is older than
  24 hours, on a background thread. **Check now** updates the same cache and timestamp. A failed
  check does not move the timestamp, but is retried at most once per hour (in-memory guard), so an
  offline device does not hit the network on every resume.
- **Showing the dialog** is decided from the cached result, separately from the check: show it when
  the cached latest is newer than `BuildConfig.VERSION_NAME`, the notify switch is on, this is a
  release build (not `0.0.0`), no stream is active (`EngineController` state), the battery prompt
  is not being shown on this launch, and `app_prompted_at` is older than 24 hours. Showing it sets
  `app_prompted_at`. So the dialog appears at most once a day, a held-back dialog is not lost, and
  turning the notify switch back on lets it appear on the next eligible return to the main screen.
- **Check now** in Settings always hits the network, updates the cache, and reports errors
  ("Could not reach GitHub", HTTP status) in the Updates section.
- "Not now" only closes the dialog; `app_prompted_at` keeps it away for a day.

### Changelog

- Shown in an in-app dialog or screen, scrollable and readable with a D-pad.
- Content: the notes of every stable release newer than the installed one, newest first, each
  under its version heading. Fetched when the dialog opens (so at most once a day) or when the user
  opens the Settings changelog, from
  `https://api.github.com/repos/outpace-stream/outpace-android/releases?per_page=30`, using the
  existing list parsing extended with `body`. This is the only API use.
- Markdown is rendered as plain readable text: strip link syntax down to the link text, drop the
  "New Contributors" and "Full Changelog" boilerplate, keep bullets. Exact rendering is the
  builder's call; it must not need a WebView or a Markdown library.
- If the API fails or is rate limited, say so and offer to open the release page in a browser
  when one exists (`Intent.ACTION_VIEW`, guarded like `BatteryPrompt.request`).

### Updating

1. Download `outpace-android-X.Y.Z.apk.sha256`, then the APK, into a dedicated directory under
   `cacheDir` (e.g. `cacheDir/app-update/`). Delete anything else in that directory first, so at
   most one APK is ever stored. Show progress and a Cancel button.
2. Verify the SHA-256 against the checksum file. On mismatch, delete the file and show an error.
3. Install with the `PackageInstaller` session API (works on API 21+, needs no `FileProvider`).
   Android returns a "pending user action" intent; launch it to show the system install screen.
   Report failure statuses (for example a signature mismatch) in plain words.
4. **Install permission**: add `android.permission.REQUEST_INSTALL_PACKAGES`. On API 26+, if
   `packageManager.canRequestPackageInstalls()` is false, explain in one sentence that Android
   needs "Install unknown apps" allowed for outpace, then open
   `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` for the package; when the user returns, continue
   if it is now allowed. Some TV builds lack that screen: fall back gracefully with instructions.
   On API 21 to 25 the global "Unknown sources" setting applies; the system install screen tells the
   user if it is off.
5. The downloaded APK is deleted after a successful install (on next start, when the installed
   version is at least the downloaded one) or on failure/cancel.

Updating replaces the app process. A running engine service is stopped by the install. The
automatic dialog never appears while a stream is active (see Checking). When the user starts an
update from Settings while a stream is active, warn first ("Playback will stop") and continue on
confirmation.

If the `PackageInstaller` session cannot complete (some vendor or TV builds block it), there is no
second install route (decision: no hand-written `FileProvider`). Show the failure plainly, keep
the verified APK until the user leaves the Updates section, and show the release page URL so the
user can install it another way.

### State (new `Prefs` keys)

- `app_update_notify` (Boolean, default true): the notify switch.
- `app_latest_version` (String?) and `app_latest_checked_at` (Long): last successful check.
- `app_prompted_at` (Long): when the automatic dialog was last shown.

Nothing else is persisted. No per-version "skip" list.

## Testing

- Unit tests (JVM, like `ReleasesTest.kt`): version comparison for the app (newer, equal, older,
  `0.0.0`), redirect parsing for the app repo, checksum file parsing, release-notes cleanup,
  "should check" and "should prompt" decisions (notify off, checked or prompted within 24 h,
  failed-check retry guard, dev build, active stream, older/equal latest).
- Engine release tests keep passing unchanged after generalising `Releases`.
- Manual check on an emulator (phone and TV image): install a signed older release, see the
  dialog, open the changelog, update, confirm the new version, confirm "Never ask again" stops the
  dialog and Settings still updates. Without signing secrets locally, this needs two signed
  release APKs or a temporary local keystore used for both builds.

## Left to the builder

- Class and file names, layout XML, string wording (no em dashes in user-facing text or docs).
- Changelog presentation (dialog vs. activity) as long as it is D-pad friendly.
- The exact hook in `MainActivity` that keeps the battery prompt and the update dialog from
  showing together (the battery prompt wins on a launch where it shows).
